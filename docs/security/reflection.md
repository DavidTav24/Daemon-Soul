# Security reflection

The security review started from the published Ashgate page, not from a checklist of bugs I hoped to find. The game is a Python platformer. In the terminal it reads the keyboard. On GitHub Pages the same package runs in Pyodide inside `index.html`. There is no application server, no database, and no account. That fact decided which findings were real.

The issues that held up were small and local. The frame was assigned to `innerHTML`. The encoder escaped angle brackets, but it was an untested function in the page. A load error appended `error.message` to the status line. Command names were used as enum keys, so a name that was not a command raised `KeyError`. The Pyodide file was loaded from a CDN with a version in the URL and no hash. pytest 8.4.2, used only for tests, matches PYSEC-2026-1845, and the fixed release does not install on Python 3.9. Score and level exist only in the browser.

The most significant of these is the CDN script. The other issues affect one page, and only if a string or a failure goes the wrong way. A replaced `pyodide.js` runs as script in every browser that opens the site. Integrity checking does not make the CDN trustworthy forever. It makes a silent substitution fail. I hashed the file I intended to load and set that hash on the script tag. I also added a Content-Security-Policy so a script cannot come from an arbitrary host. Pyodide still downloads more files after the loader, and those files are outside the hash. Saying the supply chain is closed would be false.

Cursor's useful catches were the `innerHTML` sink, the habit of printing exception text, and the reminder to scan dependencies. Those matched the source. I could point at the line. The dependency advisory also matched `pip-audit`, and pip itself confirmed that pytest 9.0.3 is not an option here. That is the right shape of an AI-assisted review: a candidate, then a tool or a test that shows the candidate is true.

Cursor also reached for vulnerabilities this program does not have. A generic web review asks for SQL injection, cookie flags, CSRF tokens, and a server that must not trust `score = 5000000`. I looked for those sinks. There is no query, no cookie, and no POST. The score lives in `GameSession` in the tab that is playing. A modified client can change that number on its own screen. It cannot submit the number anywhere, because nothing is listening. Calling that a broken authorization check would have meant building an account system so the writeup had something to fix. I recorded it as a limitation and added a narrow guard: `_begin_level` rejects a level outside 1, 2, and 3, a score that is not a modest integer, and a shield flag that is not a boolean. That is defense in depth on a function, not a login page.

Bandit was the clearest false comfort. It scanned `src/game` and reported no issues. That result is true and incomplete. Bandit does not open `index.html` and does not run the frame. The HTML sink was invisible to it. A clean scanner report is evidence about the rules that scanner knows, not evidence that the program is safe.

I separated real issues from false positives by asking what input exists and where it is consumed. If I could not find a place where an attacker outside the tab supplies the value, I did not write a fix that pretends they can. If I could find a sink, I wrote a test that feeds a harmless hostile value and asserts the sink does not treat it as code. The image tag with an `onerror` handler is the example. The test requires `&lt;img` and forbids a real `<img` tag. I did not fire that payload at any site except this project.

The easy fixes were the command allowlist and the generic error string. Both are small, and the tests say exactly what they reject. The harder fix was the Content-Security-Policy. Pyodide needs `unsafe-eval` and WebAssembly, so a strict policy that blocks those also blocks the game. I had to leave those exceptions in and say so. Integrity on the loader was straightforward once the hash was computed locally. Upgrading pytest was not a code change I could honestly make. The secure version does not run on the class machine's Python. Pinning the known version, and writing that down, is the accurate remediation.

Play was the regression check I cared about. The security tests reject bad levels and bad command names, and they still let RIGHT plus UP jump. The full pytest suite passed. In the browser, Enter still starts the meadow and walking right still moves `@` and collects the coin. The colors still come from the palette. I did not remove a gate, a control, or the shield to make the review look stricter.

The original assumption was that a single-player game has no security boundary. That is true for a shared scoreboard, which this game does not have. It is not true for the browser page. The page still pulls code from the network, still turns a string into HTML, and still shows failures to the person sitting there. Those are boundaries even when the only victim is the person who opened the tab.

I would not deploy AI-generated code, including this game, on the strength of the model that wrote it. The model built a game that plays. It also left an HTML sink without a test and a third-party script without a hash, and a generic review would have "fixed" a server this repository does not contain. The useful loop was the same one as the earlier debugging: read the function, try the bad value, keep the change that the test and the browser both survive.
